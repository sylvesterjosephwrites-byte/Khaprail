# Khaprail Tiles — UX / UI / HCI / Functionality / Codebase Audit

**Scope:** live production site at khaprail.vercel.app, plus the `khaprail-website` codebase and the live Supabase database. Read-only — no code, content, or configuration was changed as part of this audit.
**Date:** 2026-09-10.

**Method note (viewport testing):** this environment's browser-automation tool cannot actually change the rendered viewport — `resize_window` calls to 390×844 and 800×900 were accepted but the page kept rendering at the real desktop window size (confirmed live: screenshots stayed ~1536–1568px wide regardless of the requested size, and a direct `window.innerWidth` check stayed at 1536px throughout). This is a limitation this project's own `00-PROGRESS.md` session log has flagged repeatedly across many prior batches, not something new to this audit. All live screenshots below are therefore from one real desktop viewport (~1536–1568 CSS px, squarely in the "laptop/standard desktop" range). Mobile/tablet findings combine that constraint with direct source-code review of the responsive Tailwind classes (`sm:`/`md:`/`lg:`) and the dedicated mobile components (`MobileTabBar`, `MobileNav`, `MobileFiltersDrawer`). A repo-wide grep found **zero** uses of `xl:`/`2xl:` breakpoints, and every homepage/PDP section is wrapped in `max-w-7xl` — so above 1024px the layout is provably static, meaning the one live capture is a valid stand-in for both the "laptop" and "large desktop" ranges. Only true sub-1024px on-device rendering could not be independently confirmed live; that gap is called out explicitly wherever it applies rather than silently assumed away.

**Data ground-truth:** live Supabase row counts were queried directly (not inferred from screenshots) and are cited throughout — this turns several findings from "looks empty" into "confirmed empty, here's why, and here's the real data that exists one level away instead."

## 1. Executive Summary — Top 5 Issues by Impact

1. **The homepage's first "browse" click leads new visitors to a dead end, even though matching inventory exists.** The Feature Row ("Shop Wall Tiles" / "Shop Floor Tiles" / "Shop Roof Tiles" — the second thing on the page after the hero) and the Featured Categories icon rail both link straight to the root categories `wall-tiles`, `floor-tiles`, `roof-tiles`, which have **0 directly-attached products** (confirmed via SQL: `select category_id, count(*) from products group by 1`). 8 real Floor Tiles products exist, but only under the child category `Terracotta Floor Tiles`, which nothing on the homepage points to. Live-verified: `/categories/floor-tiles` shows *"Products in this category are coming soon."* while the unlinked `/categories/terracotta-floor-tiles` shows all 8 real products. `sample_inquiries` has **0 rows since launch** — there is a plausible, direct line between this broken first-click and that number. See §3.1.
2. **Client-side navigation doesn't reset scroll position — a sitewide bug on every internal link.** No route in `src/App.tsx` uses React Router's `<ScrollRestoration>`, and a repo-wide grep of `src/` turns up no `window.scrollTo`/scroll-reset logic anywhere outside the AI chat panel's own message list. Live-reproduced: scrolling to the bottom of `/products`, clicking a product card, and landing on `/products/hexagon-terracotta-tile` already scrolled to that PDP's own *bottom* ("Explore More Products" rail) instead of its top (name, gallery, "Get a Sample"). Any visitor who scrolls before clicking a link — which is most browsing behavior — lands on the wrong part of the next page and may reasonably conclude the click did nothing. See §5, Functionality table.
3. **"Trending" and "New" badges are not driven by any real signal, and currently cover close to the entire catalog.** `TrendingCategoriesGrid` picks categories via `getRootCategories(categories).slice(3, 7)` (`src/components/home/trending-categories-grid.tsx:25`) — a hardcoded positional slice, not popularity data — and 3 of the 4 categories it surfaces (Outdoor, Kitchen, Bathroom Tiles) have 0 products. The "New Arrival"/"NEW" badge logic is a 30/60-day `created_at` window, which is true of nearly every row today since the catalog was bulk-inserted in one session — so the badge currently applies to almost every product and category card sitewide, giving it zero signal value and undercutting the Von Restorff/isolation-effect principle `02-DESIGN-SYSTEM.md` itself calls for. See §2, findings 1.2/2.2.
4. **The `/products` filter system — a named, spec'd core feature (`04-PRODUCT-LISTING-FILTERS.md`) — is completely non-functional live, because `filter_types` has 0 rows**, not because of a code bug. No filter chips render on desktop, and the correctly-built mobile filters drawer has nothing to show. The admin panel to populate it (`/admin/filter-types`) works correctly and is simply unused. See §3, finding 2.3.
5. **Four different homepage sections all do "browse tiles by category," two of them almost identically.** In scroll order: Featured Categories icon rail (all 15 categories) → Trending Categories (4-category subset) → Explore Our Range (heading + 3 large photo cards + caption) → Tiles for Every Space (heading + 3 large photo cards + caption, immediately below, visually near-identical in shape). This is a textbook Hick's Law violation — more choices at the same decision point without added value — and it compounds finding #3, since one of the four sections is built on a fabricated "trending" signal. See §2, finding 2.2, and §4 (Choice overload).

## 4. HCI / Cognitive Load Findings (Part 3)

### 5-second test (homepage)
- **What Khaprail sells** — communicated in ~1–2 seconds: the hero headline ("Clay Roof & Terracotta Tiles, Shaped in Lahore Since 1982") sits over a full-bleed photographed-tile background. Clear and fast.
- **Who it's for** — implied rather than stated ("made for real Pakistani homes, not just a showroom"), reasonably fast to infer (construction/renovation decision-makers in Pakistan) but a half-step slower than the "what."
- **What to do first** — clear and fast: two large, high-contrast buttons ("Get a Sample," "Download Catalog") sit directly under the subhead, both comfortably above the 44px Fitts's-Law minimum (`h-14 px-7`). Nothing else in the hero competes for attention.
- **What slows things down** — not the hero itself, but the very next scroll: Featured Categories, Offers, and the Feature Row arrive in rapid succession, and (per §3.1) the single most obvious first click available — "Shop Floor Tiles" — doesn't lead anywhere. The 5-second *read* is good; the *first real interaction* is where the site currently loses people.

### Task-completion-time estimates

| Task | Path taken | Estimate | Outcome |
|---|---|---|---|
| Find a tile suitable for a bathroom floor | Homepage → mega-menu or icon rail → "Bathroom Tiles" → category page | 2 clicks, ~15s | **Fails.** Both `Bathroom Tiles` (root) and `Bathroom Floor Tiles` (its subcategory) have 0 products (confirmed via SQL — every bathroom-related category is empty). A visitor doing exactly this realistic task has no successful path through browsing; only the AI chat widget or a WhatsApp message escapes the dead end. |
| Request a sample of a specific product | Search "disco" → PDP → "Get a Sample" → pre-filled WhatsApp handoff | 3 clicks, ~20–30s | **Succeeds, and succeeds well.** Debounced search, a 3-field dialog with a correct pre-filled message, a WhatsApp deep link that opens with the right number and text. The site's strongest flow. |
| Understand pricing for a bulk order | Homepage "Bulk Pricing" offer card → "Shop now" → `/contact` | 2 clicks, then a manual conversation | **Partial.** Honest — 0 of 17 products have a `price` value set (confirmed via SQL), so nothing is fabricated — but there's no structured "tell us what you need" step; the visitor lands on the same generic WhatsApp CTA as every other inquiry type, with no way to pre-specify product or quantity before messaging starts. A real gap between the offer card's specific promise ("Special Rates for Large Orders") and the generic flow behind it. |

### Choice overload (Hick's Law)
In scroll order, the homepage presents: Hero (2 CTAs) → Featured Categories (15 items) → Offers (4 cards) → Feature Row (3 cards) → Trending Categories (4 items) → Explore Our Range (3 cards) → Tiles for Every Space (3 cards) → Shop by Category (3 tabs × up to 8 products) → Trending in Tiles (4 tiles) → New Arrivals (8 products). That is **4 separate category-choice moments** and **3 separate product-carousel moments** before the footer. Because the real catalog is small (17 products, only 3 categories populated), the same handful of products — Disco Tile, Murlee Tile, Spanish Tile, and similar — recur across Shop by Category, the categories Trending in Tiles links to, New Arrivals, and PDP "You May Also Like" rails. A visitor who scrolls the whole page sees several of the same products two or three times under different section titles, adding scanning cost without adding information — the definition of a Hick's Law violation, and it compounds §3.2's redundant-sections finding directly.

### Recognition vs. recall
The category badge/icon system (photo-or-icon plus a visible label, used consistently in the mega-menu, icon rail, and category-detail subcategory rows) is a genuine recognition-over-recall strength — nothing asks a visitor to remember a category name from an earlier screen. The one recall-adjacent surface is the AI chat's quick-refine chips, meant to read from `filter_types`; since that table is empty, the chips correctly don't render at all rather than showing broken placeholders (consistent with the "honest data only" rule) — not a current problem, but worth a second look once real filter values exist, since a chip a visitor has to recall from an earlier turn is a known weak pattern for that UI shape.

### Accessibility scan summary
- **Alt text:** decorative category/product photos consistently use `alt=""` paired with a visible adjacent text caption (e.g. `feature-row.tsx`'s `Shop {category.name}` label) — correct practice, not a gap.
- **Icon-only controls:** spot-checked controls (chat trigger, chat close/reset, mobile drawer close) carry real accessible names via `aria-label` or visually-hidden text — confirmed via the live accessibility tree, e.g. `button "Chat with Khaprail Tiles AI assistant"`. The gap is sizing (5.7), not labeling.
- **Form labels:** the Sample Request dialog's Name/Phone/Message fields and the admin editors' fields all use real `<label>` associations, not placeholder-only labels — confirmed via the accessibility tree on `/products/hexagon-terracotta-tile`.
- **Heading order:** no skipped levels or duplicate `h1`s found on any page checked; the one issue is missing headings entirely on two homepage sections (1.7/5.12), not misordering.
- **Focus states:** every interactive primitive built on the shared `Button`/`Link`/form components carries `focus-visible:ring-3 focus-visible:ring-ring/50` consistently (confirmed via source review across `button.tsx`, `category-tile.tsx`, `feature-row.tsx`, and others) — no instance of `outline-none` found without a paired focus-visible replacement. This is a real, sitewide strength worth naming alongside the contrast/sizing gaps above.
- **Contrast/sizing failures:** see UI findings 1.3, 1.4, 1.5, 1.6 above — the admin Sign Out button (near-zero contrast), the "NEW" badge on Trending in Tiles (3.47:1), full-opacity `bg-muted` text panels (4.33:1), and icon-only buttons under 44px.

## 7. Responsive Breakpoint Notes

**Mobile (~360–430px):** Not independently viewable live in this environment (see Method note). Based on source review: the mobile-only nav stack (`MobileTabBar`, `MobileNav`, `MobileFiltersDrawer`, all gated `lg:hidden`/`hidden lg:*`) is purpose-built, and its own layout math (a `grid-cols-5 h-16` bottom bar) clears the 44px touch-target guideline comfortably. The confirmed exception is the shared `Button` `icon`/`icon-lg` variants (1.6/5.7) used inside the AI chat panel and some sheet-close controls, both under 44px regardless of viewport. The contrast failures (1.3, 1.4, 1.5) and the missing empty-photo fallback (1.1) apply identically at every viewport size, since none of them are viewport-conditional.

**Tablet (~768–1024px):** No tablet-specific (`md:`) navigation branching exists for the pages audited — only a few grid-column-count changes (e.g. `sm:grid-cols-4` on Trending Categories). The site effectively has two real layout modes: below `lg:` (1024px) = mobile nav stack, at/above `lg:` = desktop nav + `FilterBar`. `sm:`/`md:` only reflow grids within those two modes rather than offering a distinct "tablet" experience. Reasonable for a catalog site at this stage, not a defect — flagged only because the brief asked for tablet to be reported on separately and there isn't a materially different tablet experience to describe.

**Laptop / standard desktop (~1280–1440px) and Large desktop (~1920px+):** Confirmed via source (no `xl:`/`2xl:` classes anywhere; every section wrapped in a centered `max-w-7xl`) that these two ranges render identically to each other and to the one live-captured ~1536–1568px viewport — content caps at 1280px, and any extra width becomes side margin on the flat background color. Defensible (keeps line lengths and photo sizes reasonable) but means a 1920px+ visitor sees noticeably more empty margin than content, which is worth a deliberate design call if the brand wants large-desktop screens to feel more "filled in" rather than simply wider-margined.
